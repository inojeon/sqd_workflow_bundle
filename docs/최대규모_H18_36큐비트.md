# 최대 규모 시험: H₁₈ 36큐비트, 고전 대각화 D = 10⁸

> **실행일:** 2026-10-08~09. **목적:** 양자 쪽은 에뮬레이터 한계(36큐비트)로, 고전 쪽은 PySCF 대각화 한계(배치당 D 10⁸)로 최대한 키운다. **문제:** 수소 사슬 H₁₈(1.0 Å 간격, STO-6G), 궤도 18개·전자 (9,9) 반 채움 = 36큐비트, D 상한 2.4×10⁹. **한 줄 요약:** D = 10⁸ 대각화를 3노드에서 67분에 끝냈다(배치당 33분, rank당 30 GB). 에뮬레이터는 이 넓은 분포의 36큐비트 상태를 **틀리게** 계산해(원인 진단 중), 대각화 입력은 정확 샘플러(ffsim)로 만들었다.

## 2. 왜 H₁₈인가

앞선 N₂/cc-pVDZ 36큐비트 시험([36큐비트 실행 결과](36큐비트_실행.md))에서 대각화 크기는 큐비트 수가 아니라 **샘플에 나온 스핀 문자열 수의 제곱**이 정한다는 것을 확인했다. N₂(전자 10개)는 D 상한이 7.3×10⁷이고 LUCJ 상태가 좁아 D가 2×10⁵에서 멈췄다.

반 채움 계는 상한이 크고(H₁₈: 2.4×10⁹) 강상관이라 분포가 넓다. ffsim 정확 분포로 센 스핀 문자열 수는 다음과 같다(합집합, `symmetrize_spin`).

| shot 수 | LUCJ 2회 | LUCJ 4회 |
| ---: | ---: | ---: |
| 10⁴ | 6,913 (D 4.8×10⁷) | 5,013 |
| 10⁵ | **21,414 (D 4.6×10⁸)** | 15,601 |
| 10⁶ | 39,267 (D 1.5×10⁹) | 31,505 |
| 10⁷ | 47,629 (D 2.3×10⁹) | 43,776 |

LUCJ 2회가 4회보다 분포가 넓어(CCSD 진폭 초기화 특성) 2회를 썼다.

## 3. STEP 4 대각화 규모

같은 ffsim 10만 shot을 입력으로 `max_dim`만 바꿔 D를 키웠다(`slurm/submit_step4.sh`). SQD 설정은 IBM 원문대로(배치 3, `spin_sq=0.0`, `max_cycle=200`)이고 모두 2회 반복에 수렴했다.

| 배치당 D | `max_dim` | 노드 × rank × 코어 | 풀이/반복 | STEP 4 전체 | rank당 메모리 | E (Ha) | − CCSD(T) |
| ---: | ---: | --- | ---: | ---: | ---: | ---: | ---: |
| 10⁶ | 1,000 | 1 × 3 × 10 | 85초 | 180초 | 0.6 GB | −9.64752 | +87.5 mHa |
| 10⁷ | 3,162 | 1 × 3 × 10 | 683초 | 1,377초 | 3.4 GB | −9.70913 | +25.9 mHa |
| **10⁸** | **10,000** | **3 × 1 × 32** | **1,998초** | **4,013초** | **30 GB** | **−9.72993** | **+5.1 mHa** |

- **비용은 D에 거의 비례한다.** D 10⁶ → 10⁷은 8배(코어 수 같음), 10⁷ → 10⁸은 코어를 3.2배 늘려 2.9배였다. D 10⁸ 한 배치는 32코어로 33분이다.
- **노드마다 배치 하나(L2)가 D 10⁸의 실행 방식이다.** 배치 3개를 노드 3개에 하나씩 두어 rank당 32코어·30 GB를 쓴다. 한 노드(1 TB)에 세 배치를 같이 두어도 메모리는 되지만 코어가 10개씩으로 줄어 느려진다.
- **더 키우려면:** 이 샘플(스핀 문자열 21,414개)의 상한은 D 4.6×10⁸이다. ffsim 100만 shot(39,267개)을 쓰면 1.5×10⁹까지 가능하다. D 10⁸ 측정으로 외삽하면 D 4.6×10⁸은 노드당 약 2.5시간, 140 GB다. 상한 2.4×10⁹(1천만 shot)은 PySCF 한 배치가 노드 메모리(약 700 GB)에 걸린다.
- **정확도:** D 10⁸에서 CCSD(T)보다 5.1 mHa 높다. D가 10배 늘 때 오차가 3.4~5배 줄었다.

## 4. 에뮬레이터 샘플 불일치 (진단 중)

같은 H₁₈ LUCJ 2회 회로를 에뮬레이터(pennylane-lightning-MPI v3 `mpi_counts_cli --fuse all`, 3노드 64 rank 22·21·21)로 돌린 10만 shot은 ffsim 정확 분포와 맞지 않는다.

| 지표 | 에뮬레이터 | 정확(ffsim) 10만 shot |
| --- | ---: | ---: |
| 고유 비트열 | 54,103 | 95,778 |
| 스핀 문자열(합집합) | 8,588 | 21,414 |
| 가장 흔한 비트열의 비율 | 2.6% (정확 확률 0.03%) | 0.04% |
| 정확 샘플 1천만 개에 한 번도 없는 비트열 | 고유의 65%, shot의 42% | — |
| 상위 200 χ² p-value | 0 | 0.3~0.96 |
| 전자 수 (9,9) | 100% | 100% |

전자 수와 스핀 대칭은 맞고 궤도 점유수가 전체적으로 다르다. 즉 분포가 흐려진 것이 아니라 **다른 상태**를 샘플링했다. 에뮬레이터 자체는 다음 조건에서 모두 정확했으므로(`validation/h18_36q/emulator_diag/`), 원인은 36큐비트 규모에 특정된 것으로 좁혀졌다.

| 시험 | 결과 |
| --- | --- |
| 회로 → QASM 변환(H₈ 16큐비트, LUCJ 2회) | 정확 분포와 TVD 1×10⁻¹⁴ |
| 16큐비트, 1노드 4 rank, v2·v3 | 일치 |
| 28큐비트 H₁₄, 1노드 16·64 rank | 일치 |
| 28큐비트 H₁₄, **3노드 64 rank(22·21·21)** | 일치 (49초) |
| 32큐비트 H₁₆, 3노드 64 rank | 일치 (15분) |
| 28큐비트 H₁₄ LUCJ 4회(게이트 6,574개 > H₁₈의 6,170개), 3노드 64 rank | 일치 |
| 36큐비트 N₂(좁은 분포), 3노드 64 rank | 일치 |
| 30큐비트(넓은 분포), 1노드 rank 1개(로컬 30큐비트)·4개 | 일치 |
| **36큐비트 H₁₈(넓은 분포), 3노드 64 rank** | **불일치** |

- 다중 노드 균형 분배, rank 수, 게이트 수는 원인이 아니다.
- 로컬 크기 가설(rank당 로컬 큐비트 30개 = double 2³¹개에서 32비트 인덱스가 넘침)은 **기각**됐다. 30큐비트 회로를 rank 1개(로컬 30큐비트, 105분)와 4개(로컬 28큐비트, 27분)로 돌린 결과가 모두 정확 분포와 일치했다(작업 3099, kqsvr04).
- 남은 가설: **전역 인덱스가 2³²를 넘는 상태**(물리 큐비트 32~35가 1인 성분)에서 틀린다. 32큐비트까지는 전역 인덱스가 32비트에 들어간다. N₂ 36큐비트에서 물리 큐비트 32~35는 가장 높은 가상 궤도(16·17번)의 스핀 궤도라 점유가 거의 없어 드러나지 않았을 수 있고, H₁₈에서는 이 궤도의 점유가 0.16~0.20이다.
- **검사 방법:** 34큐비트의 넓은 상태(H₁₈ 사슬, 궤도 17개·전자 (9,9))를 3노드 64 rank로 돌리면 가른다(약 1.5시간). 틀리면 33큐비트 이상 전역 인덱스 문제, 맞으면 36큐비트 고유 문제다.
- 에뮬레이터는 qc-cloud 쪽 소프트웨어라 이 번들에서 고치지 않는다. 재현 조건(36큐비트 QASM, 명령, 비교 스크립트)은 모두 보관했다.

## 5. 실행 방법

```bash
# STEP 1~3 (ffsim 정확 샘플러, 1천만 shot, STEP 4 생략)
slurm/submit_scaled.sh -p h18_sto6g_36q -a "--n-reps 2 --shots 10000000" -s ffsim -W kqsvr04 -w kqsvr04 -f 32 -T 04:00:00 -K
# STEP 4 를 D 10⁸ 로: 앞쪽 10만 shot, max_dim 10000, 3노드 × 1 rank × 32코어
slurm/submit_step4.sh -r <run_dir> -t d1e8 -s 100000 -x "--set max_dim=10000 --set samples_per_batch=100000" -N 3 -n 3 -c 32 -T 10:00:00
# 에뮬레이터 경로(참고): -s emulator -N 3 -P 64
```

원자료: [validation/h18_36q/](../validation/h18_36q/) — `summary.json`(STEP별 기록), `sacct.txt`, `step4_logs.txt`, `emulator_diag/`(진단 비교 JSON·로그).
